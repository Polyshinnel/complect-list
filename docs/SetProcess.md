# Процесс получения сетов, расчёта цен и доступного количества

## Общая схема

В проекте цепочка работы с сетами обычно состоит из трёх artisan-команд:

1. `php artisan set-list:get-set-list`
2. `php artisan set-list:update-product`
3. `php artisan set-list:calculate-price-quantity`

Они также добавлены в планировщик и запускаются каждые 10 минут через `app/Console/Kernel.php`.

Логически это одна цепочка:

1. Получаем внешний список сетов.
2. Привязываем каждый сет к нужному провайдеру по бренду.
3. Создаём или обновляем состав сета в БД.
4. Обновляем остатки и цены товаров, входящих в эти сеты.
5. По остаткам товаров считаем цену сета и максимальное доступное количество сетов для заказа.

## Основные сущности и таблицы

### `providers`

Справочник поставщиков. Создаётся миграцией `2025_09_24_130653_create_providers_table.php`.

Текущие сидовые значения:

- `FineDesign`
- `Kitchenhold`

Провайдер используется как общий ключ для:

- запроса товаров в ABC;
- разделения сетов с одинаковым SKU между разными поставщиками;
- фильтрации выдачи готового списка сетов.

### `provider_brands`

Таблица соответствия бренда и провайдера. Создаётся миграцией `2025_09_25_073911_create_provider_brands_table.php`.

Основные поля:

- `provider_id`
- `name`
- `normalized_name`

Она нужна для маршрутизации входящего сета к правильному поставщику. В коде бренд из внешнего списка приводится к lowercase и ищется по `normalized_name`.

Если бренд не найден в `provider_brands`, такой сет вообще не попадёт в дальнейшую обработку.

### `products`

Таблица товаров-компонентов сета.

Создаётся и расширяется миграциями:

- `2024_10_23_064444_create_products_table.php`
- `2025_03_12_122941_add_opt_product_price.php`
- `2025_09_24_130859_add_provider_to_products_table.php`

Основные поля:

- `id`
- `name`
- `sku`
- `price`
- `quantity`
- `opt_price`
- `provider_id`

Здесь хранится текущее состояние каждого товара, из которого собираются сеты.

### `set_lists`

Главная таблица сетов.

Создаётся и расширяется миграциями:

- `2024_10_23_114256_create_set_lists_table.php`
- `2025_03_12_122958_add_set_opt_price.php`
- `2025_09_24_130914_add_provider_to_set_list_table.php`

Основные поля:

- `id`
- `variant_id`
- `name`
- `sku`
- `brand`
- `price`
- `quantity`
- `opt_price`
- `provider_id`

Здесь хранится карточка сета и уже рассчитанные значения:

- розничная цена;
- оптовая цена;
- доступное количество сетов.

### `set_products`

Связующая таблица между сетом и товарами, из которых он состоит.

Создаётся миграцией `2024_10_23_114421_create_set_products_table.php`.

Основные поля:

- `set_id`
- `product_id`
- `variant_id`
- `sku`
- `set_quantity`

`set_quantity` показывает, сколько единиц конкретного товара нужно для одного сета.

## Источник данных по сетам: `GetSetList`

Команда: `app/Console/Commands/SetList/GetSetList.php`

Она запускает процесс загрузки и сохранения списка сетов.

### Шаг 1. Получение сырого списка сетов

Источник: `app/Http/Requests/SetListRequest.php`

Метод `getFdSetListRequest()` делает `GET` на:

`https://liberty-jones.ru/index.php?module=ListSetFDView&key=aZBcNu0V8mXA`

Из кода видно, что на вход дальше ожидается массив сетов со структурой примерно такого вида:

```php
[
    'variant_id_set' => 123,
    'product_name' => 'Название сета',
    'set_sku' => 'SET-001',
    'brand' => 'Liberty Jones',
    'items' => [
        [
            'variant_id' => 456,
            'sku' => 'ITEM-001',
            'count' => 2,
        ],
    ],
]
```

Используемые поля подтверждаются в `SetService` и `SetProductService`:

- у сета: `variant_id_set`, `product_name`, `set_sku`, `brand`, `items`;
- у товара внутри сета: `variant_id`, `sku`, `count`.

### Шаг 2. Определение провайдера по бренду

Источник логики: `app/Service/ProviderService.php`

Метод `addProductsToProvidersArray()`:

1. Загружает все записи из `providers` и `provider_brands`.
2. Строит карту `normalized_name -> provider_name`.
3. Для каждого входящего сета:
   - берёт `brand`;
   - переводит в lowercase;
   - ищет соответствие в `provider_brands`;
   - группирует сет по имени провайдера.

На выходе получается структура вида:

```php
[
    'FineDesign' => [
        [...сет 1...],
        [...сет 2...],
    ],
    'Kitchenhold' => [
        [...сет 3...],
    ],
]
```

Важно:

- неизвестный бренд просто отбрасывается;
- сам внешний список сетов не хранит `provider_id`, он определяется только через `provider_brands`.

### Шаг 3. Сохранение и обновление состава сета

Источник логики: `app/Service/SetService.php`

Команда проходит по структуре `[provider => sets]` и для каждого сета вызывает:

`SetService::processingSetList(string $provider, array $setList)`

#### 3.1. Проверка, есть ли сет в БД

Метод `checkSetDb()` ищет запись в `set_lists` по комбинации:

- `provider_id`
- `set_sku`

То есть одинаковый `sku` может существовать у разных провайдеров как разные записи.

#### 3.2. Если сета ещё нет

Тогда происходит такой сценарий:

1. Берётся список товаров из `items`.
2. Вызывается `SetProductService::manageProductList(...)`.
3. Для каждого товара из состава вызывается `ProductService::getOrCreateProduct(...)`.
4. Если товара ещё нет в `products`, система делает запрос в ABC по его SKU и создаёт товар.
5. После успешной подготовки товаров создаётся запись в `set_lists`.
6. Затем создаются связи в `set_products`.

Создание сета в `set_lists` использует поля:

- `variant_id` <= `variant_id_set`
- `name` <= `product_name`
- `sku` <= `set_sku`
- `brand`
- `provider_id`

#### 3.3. Если сет уже существует

Тогда `SetProductService::manageProductList(...)` сравнивает текущий состав сета в БД и новый состав из внешнего источника.

Сравнение идёт по ключу:

- `sku`
- `variant_id`

И отдельно проверяется количество:

- в БД: `set_quantity`
- во входящих данных: `count`

Если есть любое отличие:

- новый товар появился;
- старый товар исчез;
- изменилось количество товара в сете;

то все старые записи `set_products` для этого сета удаляются и состав создаётся заново.

Важно:

- при обновлении существующего сета код пересобирает только состав в `set_products`;
- поля самого сета в `set_lists` (`name`, `brand`, `variant_id`) не обновляются.

## Получение и обновление товаров: `UpdateProduct`

Команда: `app/Console/Commands/Product/UpdateProduct.php`

Она нужна для актуализации цен и остатков по товарам, которые уже участвуют в сетах.

### Шаг 1. Получение списка SKU из БД

Источник логики: `ProductService::getDatabaseProductsSkuList()`

Метод:

1. Загружает все записи из `products`.
2. Загружает все записи из `providers`.
3. Собирает массив вида:

```php
[
    'FineDesign' => ['SKU-1', 'SKU-2'],
    'Kitchenhold' => ['SKU-3'],
]
```

То есть обновление товаров идёт не по сетам, а по всем товарам, которые уже есть в таблице `products`.

### Шаг 2. Запрос в ABC

Источник: `app/Http/Requests/ProductRequest.php`

Метод `getProductsBySku(string $provider, array $productSku)` делает `POST` на:

`https://abc.kidsberry.org/getProducts`

Тело запроса:

```json
{
  "filter": {
    "provider": "FineDesign",
    "vendorCode": ["SKU-1", "SKU-2"]
  }
}
```

Из ответа берётся массив `products`.

Из кода видно, что дальше используются поля:

- `name`
- `vendor_code`
- `price`
- `quantity`
- `opt_price`

### Шаг 3. Обновление таблицы `products`

Источник логики: `ProductService::updateProducts()`

Для каждого товара из ответа:

1. Находим запись в `products` по `provider_id + vendor_code`.
2. Сравниваем значения:
   - `quantity`
   - `price`
   - `opt_price`
3. Если хотя бы одно изменилось, обновляем запись.

Важно:

- эта команда не создаёт новые товары, она только обновляет уже существующие;
- новые товары обычно появляются раньше, на этапе `GetSetList`, через `ProductService::getOrCreateProduct()`;
- в `getOrCreateProduct()` при первичном создании товара в БД записываются `name`, `sku`, `price`, `quantity`, `provider_id`, но не записывается `opt_price`, поэтому до первого `set-list:update-product` у нового товара `opt_price` остаётся значением по умолчанию (`0`).

## Расчёт цены и доступного количества сетов: `CalculatePriceQuantity`

Команда: `app/Console/Commands/SetList/CalculatePriceQuantity.php`

Она вызывает `SetService::calculateSetPriceAndQuantity()`.

### Алгоритм расчёта

Для каждого сета из `set_lists`:

1. Загружаем все его компоненты из `set_products`.
2. Для каждого компонента через связь `SetProduct::getProductInfo()` подтягиваем товар из `products`.
3. Считаем по каждому товару:
   - сколько полных сетов можно собрать только из этого товара;
   - сколько этот товар добавляет к цене одного сета;
   - сколько этот товар добавляет к оптовой цене одного сета.
4. Итоговая цена сета равна сумме стоимостей всех компонентов.
5. Итоговое доступное количество сетов равно минимальному доступному количеству среди всех компонентов.

### Формулы

Для одного товара внутри сета:

```php
$setCurrentQuantity = floor($productInfo->quantity / $setListProduct->set_quantity);
$setPrice = ceil($productInfo->price * $setListProduct->set_quantity);
$setOptPrice = ceil($productInfo->opt_price * $setListProduct->set_quantity);
```

Где:

- `productInfo->quantity` — остаток товара на складе;
- `setListProduct->set_quantity` — сколько единиц товара нужно для одного сета;
- `setCurrentQuantity` — сколько полных сетов можно собрать по этому товару.

После этого:

- `price` сета = сумма всех `setPrice`;
- `opt_price` сета = сумма всех `setOptPrice`;
- `quantity` сета = минимум всех `setCurrentQuantity`.

В коде минимум реализован через сортировку массива компонентов по `set_current_quantity` по возрастанию и выбор первого элемента.

### Пример

Если в сете:

- Товар A: остаток `10`, в сет нужно `2`, цена `100`
- Товар B: остаток `7`, в сет нужно `1`, цена `250`

Тогда:

- по товару A можно собрать `floor(10 / 2) = 5` сетов;
- по товару B можно собрать `floor(7 / 1) = 7` сетов;
- доступное количество сета = `min(5, 7) = 5`;
- цена сета = `ceil(100 * 2) + ceil(250 * 1) = 450`.

### Что происходит, если состав пустой

Если у сета нет записей в `set_products`, то:

- `price` останется `0`;
- `opt_price` останется `0`;
- `quantity` останется `0`.

## Как связаны три команды

Нормальный рабочий порядок такой:

1. `set-list:get-set-list`
2. `set-list:update-product`
3. `set-list:calculate-price-quantity`

Почему именно так:

1. Сначала нужно узнать, какие сеты и какие товары вообще участвуют в системе.
2. Потом нужно подтянуть актуальные остатки и цены для этих товаров.
3. Только после этого можно корректно считать `price`, `opt_price` и `quantity` у сетов.

## Что именно отдаём наружу

Готовые рассчитанные сеты отдаются через маршрут:

`GET /get-set/{provider_id}`

Контроллер: `app/Http/Controllers/Set/SetListView.php`

Он вызывает `SetService::getSetList($providerId)` и возвращает массив такого вида:

```php
[
    [
        'name' => 'Название сета',
        'price' => 1990,
        'vendor_code' => 'SET-001',
        'quantity' => 5,
        'vendor' => 'Liberty Jones',
        'opt_price' => 1500,
        'picture' => null,
    ],
]
```

То есть наружу уже отдаётся не состав сета, а рассчитанная витринная запись:

- название;
- SKU сета;
- бренд;
- розничная цена;
- оптовая цена;
- доступное количество;
- `picture` пока всегда `null`.

## Важные нюансы текущей реализации

### 1. Бренды вне справочника не обрабатываются

Если `brand` из внешнего списка не найден в `provider_brands.normalized_name`, сет не будет сохранён и не попадёт в расчёты.

### 2. Новый товар сначала может иметь `opt_price = 0`

При первичном создании товара через `ProductService::getOrCreateProduct()` поле `opt_price` не заполняется. Оно становится актуальным только после следующего запуска `set-list:update-product`.

### 3. Обновление существующего сета не меняет его карточку

Если сет уже есть в `set_lists`, код проверяет и при необходимости пересобирает только `set_products`. Поля самого сета в `set_lists` не обновляются.

### 4. Планировщик не задаёт явную зависимость между командами

В `app/Console/Kernel.php` все три команды стоят отдельно и запускаются каждые 10 минут с `withoutOverlapping()`.

Это означает:

- одна и та же команда не стартует повторно, пока прошлый запуск не завершён;
- но между разными командами нет явной гарантии последовательности внутри одного тика планировщика.

Логически процесс образует цепочку, но технически команды запланированы как три независимых задания.
